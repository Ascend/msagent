# 算子代码对比分析指令

## 任务描述

以下是从 error 侧和 normal 侧提取的两个算子代码实现。请判断它们之间属于以下哪种关系：

- **matched（等价可对齐）**：两侧都是**独立算子**，功能等价（仅命名/封装/继承不同，或 N:1 融合且融合目标是真实独立算子），可建立算子级映射。
- **absorbed（1:0，不映射）**：error 侧算子在 normal 侧**没有独立的对应算子**，仅等价于 normal 侧某个算子的**内部 kernel 一段逻辑**（normal 侧把这段计算吸收进了一个更大的算子/kernel，dump 中没有独立算子）。此时**不计为匹配**，但需说明。

> 核心原则（算子级匹配）：**只有两侧都存在可被引用的独立算子时，才算成功匹配**。若一侧算子只是与另一侧某算子的内部 kernel 片段功能等价，不能视为两侧对应算子等价。

---

## 对比维度

请从以下三个维度分析：

### 1. 输入输出接口
- 两个算子的 forward 方法的输入参数**语义**、**数量**是否一致
- 返回值**数量**、**语义**是否一致
- 注意：参数名不同但语义相同仍算一致

### 2. 核心计算逻辑
- 核心的数学运算、张量操作是否完成了相同的计算任务
- 调用的高层算子（如 `torch.nn.functional.linear`）是否在功能上等价
- **硬件专属的底层 kernel 调用差异性应忽略**（如 CUDA 算子 vs 昇腾算子），只关注上层计算逻辑是否等价

### 3. 类结构与定位
- 继承的基类是否相同或功能等价
- 核心成员变量是否对应
- 在模型架构中的作用是否一致

---

## 必须忽略的差异

- 变量命名、代码排版、注释、日志、异常处理等非功能代码
- 硬件专属的底层 kernel 调用（如 CUDA kernel、昇腾 TBE 算子），只关注上层计算逻辑
- 临时变量、冗余赋值、边界检查等工程性差异

---

## 子调用展开规则

### 何时需要展开
如果 forward 方法本身是"薄封装"——内部只调用了 1 个核心函数，真正的计算逻辑在该子函数中，且该子函数**不属于**以下情况，则可以展开这一层：
- 通用底层算子 / 公共库函数（如 `torch.nn.functional.linear`、`torch.matmul`）
- 其他独立算子的方法（如其他 Module 的 forward）

### 何时不展开
- 子调用是通用底层算子或公共库函数
- 子调用是其他独立算子的方法
- 展开后会超过一层的嵌套深度

### 如何展开
如果你认为需要展开，请在分析中说明原因，并附上被展开的子函数代码。

## 输出格式

请严格按照以下 JSON 格式输出你的分析结果，不要包含其他内容：

```json
{
  "relation": "matched | absorbed | not_matched",
  "confidence": "high",
  "reason": "简要说明判断依据，列出关键证据"
}
```

- `relation`，三选一：
  - `"matched"`：两侧都是独立算子，功能等价（可建立算子级映射，计入匹配）
  - `"absorbed"`：error 侧算子仅等价于 normal 侧某算子的**内部 kernel 片段**，normal 侧无独立算子可对位（**不计匹配、不计覆盖率**，仅说明）
  - `"not_matched"`：两侧功能不等价或没有对应关系
-`confidence`：`"high"`（高度确信）、`"medium"`（中等确信）、`"low"`（低确信）
- `reason`：简短的理由说明，重点说明两侧代码在核心语义上是否对齐，判断依据是什么。若为 `absorbed`，请说明它被 normal 侧哪个算子/kernel 吸收，以及 normal_dump 中为何无独立算子。

如果展开了子调用，请在 `reason` 中说明。
